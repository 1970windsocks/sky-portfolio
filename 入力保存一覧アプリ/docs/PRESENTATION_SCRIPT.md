# 発表台本(5分)

第72課題で作成。`ARCHITECT_PROPOSAL.md`を、実際に人に話す形に落とし込んだ
もの。括弧内は目安の時間。

---

**(0:00〜0:30) 導入**

「メモを保存するだけのアプリを、12日間かけてAIサポート機能付きのSaaSに
育てました。今日は、その全体設計と、事業として売るならどうするかを
お話しします。」

**(0:30〜1:30) アーキテクチャ**

「全体はStreamlitの画面と、決済Webhookを受けるFlaskサーバーの2つに
分かれています(画面を見せる: `ARCHITECTURE.md`の構成図)。Postgres、
Stripe、Resend、そしてClaude APIと連携していて、外部APIは全部
`urllib.request`で直接呼んでいます。SDKを増やさず、小さな依存で
全体を見通せる状態を保っています。」

**(1:30〜2:30) AI機能**

「AI機能は3段階で作りました。まずカテゴリー提案のような構造化出力、
次に自社文書に答えるRAG、最後に検索→生成→評価→保存を自律的に行う
エージェントです。ここで大事にしたのは、精度を誇張しないこと。
実際に検索精度を測ったら、短い条文が誤って上位に来るケースを見つけました。
だから根拠を必ず画面に表示して、人が気づける設計にしています。」

**(2:30〜3:15) 信頼性とセキュリティ**

「可用性の目標は99.5%、月の許容ダウンタイムは216分と数字で決めています。
セキュリティは脅威モデリングで8つのフローを点検し、権限設計の欠陥や
監査ログの抜けを実際に見つけて直してきました。今日もう1つ、AI機能への
呼び出し回数に上限が無かった抜けを見つけて、その場で直しました。」

**(3:15〜4:15) 事業計画**

「このサポートエージェントは、今は管理者専用の内部ツールですが、
自社の文書はあるのに問い合わせ対応に人手を割けない小規模事業者に
売れると考えています。月1,980円のプランを想定していて、Claude APIの
実際のコストから見ても十分な粗利が出る水準です。ただし正直に言うと、
今は全ユーザー共通の1つの文書セットしか検索対象にできないので、
複数の契約者に売るには、契約者ごとにデータを分ける設計変更が前提になります。」

**(4:15〜5:00) まとめ**

「12日間で、動くものを作るだけでなく、なぜその設計にしたかを記録し、
弱い所を自分で見つけて直す、というところまでできるようになりました。
今日はその総仕上げとして、提案書全体を見直し、見つかった抜けを1つ、
実際にコードとテストで埋めています。」

## 一番の推しポイント

**「精度の限界を隠さず、根拠を見せることでカバーする設計」**。RAGや
エージェントの検索精度は完璧ではないが、それを誤魔化さずに実測結果として
公開し、代わりに「根拠を必ず表示する」という設計でユーザー側が気づける
ようにしている。AIプロダクトにありがちな「とにかく賢そうに見せる」方向
ではなく、限界を前提にした上で安全に使ってもらう設計を一貫して選んできた
点が、この12日間で一番伝えたい部分。

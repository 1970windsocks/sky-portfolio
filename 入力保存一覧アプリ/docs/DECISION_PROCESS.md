# 技術選定の決め方

第69課題で作成。技術を選ぶとき、「なんとなくこっちが良さそう」「前に使った
から」のような感情論・慣れだけで決めると、後から理由を説明できなくなる。
感情論にならない進め方を決めておく。

## 進め方

1. **選択肢を並べる(最低2つ)** — 「これしかない」と思っても、実際には
   「何もしない」も含めて常に複数の選択肢がある。第60課題のADRでは
   「同期のまま」「外部ブローカー」「インプロセスキュー」の3つを並べた。
2. **各選択肢の良い点・悪い点を書く** — 良い点だけ書くと説得のための
   資料になってしまう。悪い点(トレードオフ)も必ず書く。
3. **判断基準を先に決める** — 「今のところ何を一番優先するか」
   (例: 予算制約・実装の速さ・将来の拡張性)を選択肢を比較する前に
   決めておく。基準を決めずに比較すると、後から基準を選び直して
   結論に合わせてしまいがち。
4. **決定と理由をセットで残す** — 「Aにした」だけでなく「Bもあったが、
   ○○という基準で見るとAの方が優れていたためAにした」まで書く。
   重要な決定は`docs/adr/`にADRとして残す(第68課題)。軽い決定でも、
   最低限コミットメッセージに理由を書く。

## 最小テンプレート

```markdown
## 決めたいこと
(1行で)

## 選択肢
- 選択肢A: 良い点 / 悪い点
- 選択肢B: 良い点 / 悪い点
- 選択肢C(何もしない、という選択肢も含める): 良い点 / 悪い点

## 判断基準
今回優先するのは「○○」(例: 予算・速さ・保守性)

## 決定
選択肢○○にする

## 理由
(判断基準に照らして、なぜその選択肢が優れていたか)
```

## 使い分け

- **影響範囲が大きい・あとから覆しにくい決定** → `docs/adr/`に正式なADRとして残す
- **日々の小さな判断** → 上の最小テンプレートで十分。コミットメッセージに
  書き込むだけでもよい

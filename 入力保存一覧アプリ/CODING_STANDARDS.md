# コーディング規約

第69課題で明文化。69日間の開発で、言われなくても一貫して守られてきた
やり方を、チームの約束事として書き出した。新しく参加する人(人間でもAIでも)
が同じ基準で書けるようにするための文書。

## ① コメントは「なぜ」を書く、「何を」は書かない

```python
# 悪い例: コードを読めば分かることを書いている
# ユーザー名でDBを検索する
user = get_user_by_username(username)

# 良い例: コードだけでは分からない背景・制約・理由を書いている
# 第45課題: ユーザー名が存在するかどうかで応答を変えると、
# 列挙攻撃(ユーザー名の総当たり特定)を許してしまうため、
# 存在しない場合も同じ文言を返す。
```

変数名・関数名で言えることはコメントに書かない。コメントは「このコードが
今の形になった理由」「ハマりどころ」「過去に起きた問題との関連」を残す場所。

## ② 1つの変更は1つのPR

無関係な変更を1つのPRに混ぜない。過去に、別の課題の未コミット変更が
紛れ込んでCIが落ちた経験(第60課題)から得た教訓。急ぎでなければ、
関係ない修正を見つけても別PRに切り出す。

## ③ 「できました」と言う前に、本物のデータで確かめる

モックやダミーデータだけで「動く」と判断しない。可能な限り、本番相当の
データ・実際のAPI・実際のDBに対して動かし、結果を確認してから完了とする。
やむを得ずモックに頼る場合(外部APIのクレジット不足等)は、その旨を
正直に明記する(第63〜65課題)。

## ④ トレードオフは隠さず書く

「良い点だけ」を書かない。採用した設計が持つ弱点・制約・将来直すべき点を、
コミットメッセージやコードコメントに残す。第60課題のADR(非同期キューが
プロセス再起動で消える問題)のように、残課題を明記しておくことで、
後から読む人(未来の自分を含む)が同じ罠にハマらずに済む。

## ⑤ 新しい外部依存を増やす前に、標準ライブラリで足りないか考える

このプロジェクトは外部API呼び出しに`urllib.request`を直接使い、SDKを
追加していない(`auth.py`・`ops.py`・`ai_category.py`・`rag.py`・
`support_agent.py`すべて同じ方式)。小規模なAPI呼び出しが複数あるだけなら、
依存を増やすよりHTTP層を自分で持つ方が、全体の見通しが良いと判断している。

## ⑥ ユーザー入力には必ず長さ制限を付ける

フォームや質問欄などユーザーが自由に入力できる項目には、`MAX_TEXT_LENGTH`の
ように明示的な上限を設ける。第69課題のレビューで、AI機能への質問欄に
この制限が漏れているのを見つけて追加した(`MAX_AI_QUESTION_LENGTH`)。

## コードレビューでの言葉遣い

- 改善点は命令形ではなく提案・質問の形で書く(「〜してください」ではなく
  「〜はいかがでしょうか」「〜という理解で合っていますか」)
- 良い点を先に1つ書いてから、改善提案に入る
- 「なぜそう思うか」の理由を添える(理由の無い指摘は感情論になりやすい)
